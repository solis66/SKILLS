## 一、最稳定的核心论点：只认"代码/日志能证明的行为"

这是他**重复次数最多**的一条主张，出现在 9 条独立发言里，措辞几乎一字不改。

1. 「不要编造代码无法支持的行为」这一句作为固定收尾，出现在 9 条独立的 Archify 提示词里：`#L84 #L88 #L89 #L90 #L91 #L92 #L93 #L94 #L95` `[一手:user-turns.jsonl#L84][一手:user-turns.jsonl#L88-#L95]`
2. 把"不臆造"具体化为可执行的工程约束：「不臆造行号；挂不准的 sources 就不挂，宁可少挂」`[一手:user-turns.jsonl#L85]`
3. 把"证据优先级"写成分级规则：「不把教程的说法当结论，最终以源码为准；教程与代码冲突时以代码为准并在图里注明」`[一手:user-turns.jsonl#L85]`
4. 连"注释"都不算行为：「不把'注释掉的代码'当行为：HomePage.vue:182 的 fetchNoticeNum 是注释，真正入口是 TrendAndCollect」`[一手:user-turns.jsonl#L85]`
5. 要求产出**反向证明**：源码里没有的东西要显式标成「无审批环节（源码 0 命中）」「无重试：失败即终态」`[一手:user-turns.jsonl#L85]`
6. 遇到真实 bug 时，第一反应是"去日志里找"，而不是"猜原因"：「请你查看该项目中的 log 记录等，告诉我项目中流式缺字问题 bug 是如何出现的，如何进行修复的？」`[一手:user-turns.jsonl#L97]`
7. 在求职场景里用同一套标准对待自己：`/job-match` 连用 7 次，每次固定句式「列出每项要求的**真实证据、表达缺口和能力缺口**，并告诉我是否值得投递。**先不要改简历**」`[一手:user-turns.jsonl#L175][一手:user-turns.jsonl#L180][一手:user-turns.jsonl#L183][一手:user-turns.jsonl#L189][一手:user-turns.jsonl#L191][一手:user-turns.jsonl#L198][一手:user-turns.jsonl#L199]`

**判读**：这不是"担心 AI 胡说"的泛泛要求，而是一套有具体操作形态的证据纪律（挂行号、标负向证据、冲突时以谁为准）。它同时出现在**技术文档**和**简历**两个完全不同的场景，说明是他跨领域的通用判据。`[推测]`

## 二、自造术语与自建方法论（本维度最有复用价值的部分）

### 2.1 「负向证据」

1. 在 Archify 需求里，他把"没找到"定义为一类必须交付的证据：「审批：源码里没有审批环节。不要画审批节点，改为'网关鉴权放行判定'这一段，并额外标注一条'无审批环节（源码 0 命中）'的负向证据」`[一手:user-turns.jsonl#L85]`
2. 他把负向证据写进交付验收：「交付后回报 JSON 与 HTML 的绝对路径，并说明哪些节点是'负向证据'（无审批、无重试）」`[一手:user-turns.jsonl#L85]`
3. 在求职侧有同构做法：简历里"没做过"的项要清掉而不是模糊处理——「清掉上表 4 处 ❌（个人项目、<30s、10 倍、LeXiScan 两个数字）」`[一手:user-turns.jsonl#L178]`

**判读**：常规做法是"删掉不存在的"，他的做法是"**把不存在显式写出来**"。这是"负向证据"最核心的区别，也是他自己命名、反复使用的术语。`[推测]`

### 2.2 「真实证据 / 表达缺口 / 能力缺口」三分类

1. 这三个词绑在同一句指令里，7 次几乎逐字重复（见 §一第 7 条），构成他判断"要不要投这个岗"的固定漏斗：先看有没有真证据，再看是"会但没写清"还是"真不会"。
2. 三分类的落地是"先诊断后动手"：每次都加一句「先不要改简历」`[一手:user-turns.jsonl#L175]`，把"评估"和"改写"两个动作强制拆开。
3. 分类后他才决定改法：「补强 1、2 项：可连续 4–6 个月（2026.11–2027.05）· 每周可到岗 5 天」——补的是"表达缺口"里的硬信息，不是形容词。`[一手:user-turns.jsonl#L176]`

### 2.3 「稳妥版 / 进取版」双版本策略

1. 他反复要求同一份简历出两个定位版本：「给出稳妥版和进取版定位，改写简历要点」`[一手:user-turns.jsonl#L177][一手:user-turns.jsonl#L186]`
2. 选定后不再折中，而是重建：「重建一版安点科技 AI 全栈版（推荐，用最新干净源，天然满足第 1、2 条）」`[一手:user-turns.jsonl#L179]`
3. 他连"谁的功劳该降级"都指定：「需求梳理写主导。claude 降级成纯工具分工」——主动压低 AI 在叙述中的分量。`[一手:user-turns.jsonl#L179]`

### 2.4 「看过 ≠ 会」的三级掌握度

1. 他把掌握度切成可判定的三档：「每项标注'未学 / 看过但不能独立解释 / 能解释并完成基础题'」`[协作:articles/note-10.16-rules.md#L89]`
2. 配套红线：「**不把'已看完'当作完成：**做题先遮答案；猜对单独标记，仍列入待复测」`[协作:articles/note-10.16-rules.md#L43]`
3. "猜对"被单列成独立统计项，而不是并入正确率：「猜对题也标记为待巩固」「旧题重做正确与新题正确分开统计」`[协作:articles/note-10.15-plan.md#L15][协作:articles/note-10.16-rules.md#L53]`
4. 统计口径要能自证：「'未做'和'做了但错误'要分开」「忘记称重就如实填'未测'，不补猜测数值」`[协作:articles/note-10.16-rules.md#L153][协作:articles/note-10.16-rules.md#L143]`
5. 他自己的记录表真的按这个口径填，且填得很难看：树图 0/20、线性表 0/8、SQL 0/3 `[协作:articles/note-10.14.md#L9-L12]`

**判读**：这套"猜对单列 + 未测不猜 + 分档标注"是他**唯一**在技术、考试两个领域都稳定执行的量化方法。它与 §一 的"负向证据"是同一思维的两个投影：**把不确定性显式记账**。`[推测]`

## 三、技术主张：先问口径，再信数字

1. 看到"300ms 降到 30ms"先问缓存性质与分位：「热点视频 300ms 降至 30ms 采用的是热缓存还是冷缓存？是否测 P95？」`[一手:user-turns.jsonl#L21]`
2. 看到"检索 200ms"先问测量边界：「该项目中 ES 查询耗时还是用户端全链路耗时？」`[一手:user-turns.jsonl#L22]`
3. 看到"失败率下降 80%"先问机制：「该项目中是如何实现大文件重复上传失败率下降约 80%」`[一手:user-turns.jsonl#L20]`
4. 看到 RAG 阈值先问语义方向：「该项目中阈值 0.20 返回的是距离还是相似度」`[一手:user-turns.jsonl#L99]`
5. 看到异常码先问归属：「网关 500 和 600 的含义」`[一手:user-turns.jsonl#L87]`
6. 对数字的处置是"加限定词而不是删掉"：「把'（项目统计）'限定词加回 90%+ 与 99.5%」——他知道这些数字样本小，选择标注而非放弃。`[一手:user-turns.jsonl#L178]`

**判读**：他对**指标口径**的敏感度明显高于对**指标数值**的兴趣。四次追问（缓存性质、P95、链路边界、距离/相似度）都不是问"多少"，而是问"你怎么算的"。`[推测]`

## 四、架构与工程审美：状态机、分层、可观测

1. 长任务必须显式状态化：「将批改任务拆分为 queued、recognizing、grading、done、failed 5 种状态，通过后台线程执行 OCR 与模型调用，前端轮询进度」`[一手:articles/resume.docx.txt#L33]`
2. 职责按"接口 / 业务编排 / RAG 检索 / Agent / 模型工厂"五层切开，而不是按文件类型切 `[一手:articles/resume.docx.txt#L32]`
3. 网关收口 + 无状态鉴权：「以 JWT 长短双 Token（30min / 7d）替换 Session，鉴权无状态化」`[一手:articles/resume.docx.txt#L42]`
4. 上下文要给硬上限而不是"尽量短"：「短期记忆限制为 6 条消息、2,000 字符」「多轮会话按 12000 字符阈值滚动裁剪」`[一手:articles/resume.docx.txt#L36][一手:articles/resume.docx.txt#L46]`
5. 他会主动把"能力"收敛掉：「咨询 Agent 仅保留 1 个知识检索工具……移除批改工具以避免意图误用」——减法优先于加法 `[一手:articles/resume.docx.txt#L36]`
6. 选型理由是"下限/上限"叙事：「使用了……SpringBoot，保证了下限的基础上引用了 SpringCloud 系列组件搭建微服务提高上限」`[协作:articles/project-aigcbilibili-README.md#L18]`
7. 遇到规模问题先想编排而不是加机器：「如果突然有一百位老师同时提交批改……容器、队列、调度、限流你有什么思路」`[一手:user-turns.jsonl#L40]`

3. 对"简历同质化"有明确判断（协作产出，可能被 AI 改写）：「绝大部分 Java 人都是做的黑马尚硅谷项目或其余较流行项目，项目上的千篇一律导致 hr 及面试官对简历感兴趣程度较低」`[协作:articles/project-aigcbilibili-README.md#L17]`

## 六、审美偏好：把抽象机制"变成看得见的过程"

这是他在技术侧最一致的个人趣味，跨 5 类场景反复出现：

1. 想把整条链路做成视频：「有没有办法帮我将项目的原理以及每个链路上数据的传输弄成一个可视化的原理过程视频学习」`[一手:user-turns.jsonl#L76]`
2. 要求把 Java 代码的执行过程变成动画网页：「你是一个能够将抽象复杂算法原理转化成一个通俗易懂的动画过程的工程师……将其中各变量的变化过程清晰的展示在网页中」`[一手:user-turns.jsonl#L108]`
3. 自己动手做了算法过程展示页并接进项目：反转链表（#L100）、替换字符（#L118）、反转字符串中的单词（#L119），并按「{链表，双指针}」「字符串/双指针」打标签归档 `[一手:user-turns.jsonl#L100][一手:user-turns.jsonl#L118][一手:user-turns.jsonl#L119]`
4. 把同一冲动用在系统架构上：12 次用 Archify 把仓库链路画成泳道图（前端 API→代理→网关→服务→返回体）`[一手:user-turns.jsonl#L84-#L95]`
5. 对图的**结构**有硬要求，不是"好看就行"：「泳道（必须且只能这五条，lane id 用英文）」「主路径 10 个节点要连线清晰；A/B/C/D 四条旁支不能压在主路径上」`[一手:user-turns.jsonl#L85]`
6. 影视审美是同一种"过程可见"：他的分镜方案给每个镜头写"首帧静态状态 / 主动作弧 / 可见结果 / 必要反应 / 接力状态"，把表演拆成可检查的状态迁移 `[协作:articles/fiction-yuluo-storyboard.md#L189-L206]`
7. 色彩被他写成规则系统而非感觉：「本影片专属三色系统：铅灰、蓝黑、青绿色」「金色不能铺满画面，越稀少越神圣、越危险」「具体的色彩弧线：校园冷蓝→车厢银黑→高架铅灰→超自然暗金→结尾灰烬般的冷金」`[协作:articles/fiction-yuluo-storyboard.md#L11]`

**判读**：他的"审美"不是风格偏好，而是**约束偏好**——三色系统、五条泳道、10 个节点、"必须且只能"。给他自由度他反而要规则。`[推测]`

## 七、创作侧：写实克制 + 明确的版权边界

1. 叙事底线写得很硬：「写实克制：不说破、不狗血、靠沉默与日常细节承载情感——**底线气质，不可违反**」`[协作:articles/creative-moon-plan.md#L91]`
2. 拒绝"复刻官方风格"，只要叙事语法：「不做官方作品风格的'复刻模仿'，而是提炼其叙事语法……属于对原作气质的个人化转译」`[协作:articles/creative-moon-plan.md#L122]`
3. 授权立场是他自己选的，且选的是最保守的一档：「你选择：**仅个人练习 · 不公开发布**」，并列出四条不允许（不投稿、不商用、不分发、不声称关联官方）`[协作:articles/creative-moon-plan.md#L101-L115]`
4. 改编边界写成"既成事实不可违反"清单：「这四条是绝对不可违反的既成事实」（结局闭合、职业是公务员、六年制药学、始终未离开川越）`[协作:articles/creative-moon-plan.md#L76-L80]`
5. 会主动为"自己加的东西"打标签：「以下为导演补足，非原文事实」`[协作:articles/creative-moon-plan.md#L139]`
6. 产能约束不许美化：「**30 秒 = 6 段 5 秒**」「本机 8GB 上 I2VA 5 秒的经验值约 12 分钟/段……6 段 ≈ 1.5 小时以上，不含重试」「老实的建议是先跑通 fast 基线，再谈画质」`[协作:articles/creative-moon-plan.md#L327-L342]`

**注意（重要）**：`fiction-yuluo.docx.txt` 的正文与《龙族》楚子航雨夜章节高度重合（"爸爸是个优质、负责、有教养的好男人"等原句），分镜稿把"楚子航/仕兰中学"改为"鹿芒/翁源中学"。因此这份 docx 更像**同人改写素材或摘录，不能作为原创写作能力证据**；MANIFEST 标注的"本人创作"应下调。`[推测]`

## 八、自我管理方法论：以"可检查的产出"为唯一完成标准

1. 每天的计划不写"学什么"，写"必须留下什么结果"：「必须留下的结果」列——一棵小树的遍历结果、4 题作答与订正、一条含筛选与排序的查询 `[协作:articles/note-10.16-rules.md#L32-L41]`
2. 时间是"上限提示"而非配额：「时间是上限提示；遇到卡点，保留题号和错误步骤，不为凑题数跳过订正」`[协作:articles/note-10.16-rules.md#L30]`
3. 计划分"必做版 180 分钟 / 加做版 120 分钟"，且明确授权放弃：「只有 3 小时，当天明确顺延……17 日根据 16 日晚的实测情况重新排，不默认全部照搬」`[协作:articles/note-10.16-rules.md#L130]`
4. 用昨天的真实数据反推今天的量，而不是沿用理想值：「按 15 日实际学习 3 小时，设置**净学习 3 小时的必做版**；有余力再加做，**最多扩展至 5 小时**」`[协作:articles/note-10.16-rules.md#L8]`
5. 主动区分"官方标准"与"自设标准"：「复测目标暂设为前 18 题至少 15 题正确……这是本计划的自设巩固标准，不是官方分数线」`[协作:articles/note-10.16-rules.md#L100]`
6. 跨文件推算要留痕并允许推翻：「此处属于跨文件推算；若有跳题、补题或'44'包含复测题，晚间记录时改成实际起止题号及总题数」`[协作:articles/note-10.16-rules.md#L24]`
7. 交付也分"小样→确认→铺开"：「按运行契约：**先 1 条小样 → 你确认 → 再扩展剩余**」+ 一张逐镜"验收台账"（画面检查/声音检查/残留问题/最小恢复动作）`[协作:articles/creative-moon-plan.md#L346-L356]`
8. 医疗边界上拒绝"感觉良好"当许可：「遵守基础信息中已记录的医生'禁止力量训练'要求；**无疼痛记录不等于已获得恢复训练许可**」`[协作:articles/note-10.16-rules.md#L147]`
