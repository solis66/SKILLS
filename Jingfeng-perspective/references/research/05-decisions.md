## 1. 技术决策：接什么、改什么、放弃了什么

### 1.1 项目选题：刻意不做「黑马/尚硅谷」那一类项目

- **情境**：2025.12–2026.03 他做仿 B 站微服务项目 LABiliBili，准备用它当简历主项目。
- **可选方案**：A. 跟着主流教程做单体商城/管理系统（资料多、好抄、面试官熟）；B. 自选业务、按 B 站功能一比一复刻，自担复杂度。
- **实际选择**：B。7 个微服务 + 22 个技术栈 + 自研 AIGC 链路`[一手:articles/resume.docx.txt]`。
- **他给的理由**（写在仓库 README 里）：「绝大部分 Java 人都是做的黑马尚硅谷项目或其余较流行项目，项目上的千篇一律导致 hr 及面试官对简历感兴趣程度较低……甚至见到简历写这些项目就直接丢弃」`[协作:articles/project-aigcbilibili-README.md#L17]`。
- **事后结果**：这个判断本身有依据——他后续面经里能答出源码级细节（网关鉴权、分片合并、MQ 同步 ES）`[协作:articles/interview-qa.md]`，说明项目确实是自己啃过的，不是抄的壳。
- **注意**：这段理由是 AI 协作写成的营销文案，只能作为「他认可并保留了这个说法」的证据，不能当作他的原话。

### 1.2 大模型选型：用千问/星火，始终没有直连 OpenAI/Claude

- **情境**：两个项目都要接大模型。作文批改要打分+咨询，仿 B 站要文生文/文生图/PPT。
- **可选方案**：A. 直连 OpenAI / Anthropic 官方 API；B. 接国内厂商（通义千问、讯飞星火）；C. 只写 Prompt 不真接。
- **实际选择**：作文批改接千问，仿 B 站接讯飞星火`[一手:transcripts/user-turns.jsonl#L182]`；星火走 WebSocket + HMAC-SHA256 鉴权`[一手:articles/resume.docx.txt]`。
- **他给的理由**：**没有说明**。语料里只见到事实陈述「没有直连过 openaicgp 和 claude 的官方 api」`[一手:transcripts/user-turns.jsonl#L182]`，没见到他解释原因。`[推测]` 成本与境内可访问性是主因，但这是推测，不能写成他的判断。
- **事后结果**：这个选型后来变成了简历上的风险点——方案文档直接指出「技术栈栏写了 Function Calling、LangChain，但 LABiliBili 里没有任何落地」`[协作:articles/project-xinghuo-plan.md#L57]`。

### 1.3 明知是技术债，选择「能跑就先不动」

- **情境**：星火接入代码里三份 90% 重复的鉴权工具类、`System.exit(0)` 写在 onFailure 里、上下文只存 JVM 静态 Map。
- **可选方案**：A. 三个 demo 调通后立刻抽公共类重构；B. 先堆业务功能，重构留到后面。
- **实际选择**：B。
- **他给的理由**（面经里的第一人称自述）：「说实话是**『能跑就先不动』**。三个 demo 分别调通后，抽公共类意味着要重新验证三条链路，当时优先做业务功能了。**这个取舍我认，但它是技术债**，我在重构清单里排在第 4 位」`[协作:articles/interview-qa.md#L3339]`。
- **事后结果**：他自己给出了代价清单——重启失忆、多实例上下文分裂、第三方抖动导致整个 chat 进程退出`[协作:articles/project-xinghuo-plan.md#L77]`。这是本维度**唯一一处他明确承认「我知道该做但没做」并给出理由**的记录。
- **权重提示**：这段文字出自 AI 协作的面经文档，可能被润色过；但「先做功能后还债」与他 1.5、3.3 的行为一致，可交叉验证。

### 1.4 部署：选 docker，选便宜服务器，选「能发给别人」

- **情境**：项目做完要上线、要给别人看。
- **可选方案**：A. 只在本机跑，面试时录屏；B. 买服务器真部署；C. 打离线包发给对方自己跑。
- **实际选择**：B + C 都做了。在「2*4 的轻量级应用服务器」上部署并推 GitHub 拿部署命令`[一手:transcripts/user-turns.jsonl#L79]`；同时问「如何将该项目 demo 打包发给其他人」`[一手:transcripts/user-turns.jsonl#L80]`。
- **他给的理由**：未明说，但从动作看是要**可验证的线上地址**——简历里直接写了「http://8.134.63.226」`[一手:transcripts/user-turns.jsonl#L197]`。同类决策在 AiTeachers 也出现：要求「打包成压缩文件-解压后可以直接在本地进行构建」`[一手:transcripts/user-turns.jsonl#L96]`。
- **事后结果**：环境选型上他有明确的「容器优先」倾向。装 deer-flow 时直接定调：「走 docker 容器吧，我把 nginx 在本地安装了」`[一手:transcripts/user-turns.jsonl#L51]`。

### 1.6 他的默认解法是「装现成能力」，不是「自己写」

- **情境**：遇到任何能力缺口——识别图片文字、做架构图、改简历、管理求职进度、造自己的 skill。
- **实际选择**：几乎全部走「找现成 skill/插件装上」。语料中安装类发言至少 15 条：dsh-workbuddy-connect`[#L101]`、ASu-skills`[#L102-L105][#L134-L135]`、archify`[#L78]`、nuwa-skill`[#L125]`、claude code cli`[#L124]`、codex++`[#L128]`、「安装什么插件可以让 dp 识别图片内的文字」`[#L188]`、「如何添加 skills 在 dsh 中」`[#L148]`，均见 `[一手:transcripts/user-turns.jsonl]`。

- **事后结果**：这套「先装」策略的成本也真实发生过：archify 装了又被要求回滚卸载（见 4.3），workbuddy 国际版隔离失败后改成卸载（见 4.1）。
- **`[推测]`**：他把自己定位成「能力的装配者」而不是「轮子的发明者」，这与他把大量时间投入到工具链而非算法题的选择是一致的（见 3.1）。

## 2. 求职决策：投什么、怎么包装、投不投

### 2.1 「先不要改简历」——先判值不值得投，再动笔（5 次一致）

- **情境**：手里有 JD 和自己的简历，想投。
- **可选方案**：A. 直接按 JD 改简历再投；B. 先做证据对照、判断匹配度，再决定改不改。
- **实际选择**：B，而且**连续五次用几乎同一句话开头**：「请你对照……列出每项要求的真实证据、表达缺口和能力缺口，并告诉我是否值得投递。**先不要改简历**。」`[一手:transcripts/user-turns.jsonl#L175][#L183][#L189][#L198][#L199]`
- **他给的理由**：没有单独解释，但这句话本身就是决策规则——**先算证据缺口，再决定要不要投入改写成本**。
- **事后结果**：规则被执行了。广州高斯记忆那家，对照完直接得出「不继续我不想投递这个岗位」`[一手:transcripts/user-turns.jsonl#L190]`；另有至少 5 家进入改写阶段（易积股份、安点科技、机械星球、天高科技、艺龙酒店科技）。**至少 7 家评估 → 1 家明确拒投 → 至少 5 家进入改写**`[一手:transcripts/user-turns.jsonl#L175-L200]`。

### 2.2 包装的边界：主动删掉 4 处「说不清」的数字

- **情境**：AI 帮他改的简历版本里出现了几个他自己解释不了的量化点。
- **可选方案**：A. 留着，反正 HR 不一定问；B. 删掉，换成能讲清测量方法的表述。
- **实际选择**：B。原话：「清掉上表 4 处 ❌（个人项目、<30s、10 倍、LeXiScan 两个数字）；把『（项目统计）』限定词加回 90%+ 与 99.5%」`[一手:transcripts/user-turns.jsonl#L178]`。
- **他给的理由**：未直接说明，但同一批材料里写得很清楚：「**不要为了简历编数字**。面试官会让你讲测量方法。宁可写『-32%（自测 30 轮对话样本）』也不要写没有来源的『-80%』」`[协作:articles/project-xinghuo-plan.md#L210]`。
- **事后结果**：这才是本维度的关键——他**不是不包装，而是给包装设了一条「必须能自证」的底线**。前后两天他还主动纠正了三处事实：供应商型号（千问/星火）、耗时（<60s）、有无直连官方 API`[一手:transcripts/user-turns.jsonl#L182]`，并纠正自己在大模型项目里的角色是「主要负责 AI 咨询模块」而非主导全项目`[一手:transcripts/user-turns.jsonl#L194]`。

### 2.3 定位摇摆：Java 前置 / AI 全栈 / AI 应用，最后是「两版都改」

- **情境**：同一份经历要投不同岗位。
- **可选方案**：A. 定一个统一人设；B. 每个 JD 一版；C. 一次出两版（稳妥/进取）。
- **实际选择**：C。原话：「两版都改」`[一手:transcripts/user-turns.jsonl#L185]`；此前已分别出现过「目标岗位：AI 全栈开发实习生」`[#L177]`、「AI 应用开发实习生」`[#L186]`、「做一版 **Java 栈前置** + 教育 + AI 工具的真实表述」`[#L192]`。而最终定稿简历的求职意向写的是「AI 应用 / 后端开发」`[一手:articles/resume.docx.txt]`。
- **他给的理由**：未说明取舍理由，只给了指令。
- **事后结果**：**这是一处真实矛盾，不调和**——简历定稿是「AI 应用 / 后端开发」二元定位，但实际投递文件名是「Java+AI 应用开发实习生-双页版」`[一手:transcripts/user-turns.jsonl#L175]`，而求职自述又说「投的是 AI 开发岗位」`[#L145]`。三个说法并存，说明他的岗位定位在 2026-10 仍未收敛。

### 2.4 AI 协作怎么署名：主动把 AI「降级成纯工具」

- **情境**：简历要写「AI 辅助完成需求→设计→代码→测试」的全链路，问题是 AI 该占多大分量。
- **可选方案**：A. 写「用 AI 完成系统」（显得产出高、但等于自认不是作者）；B. 写「主导需求梳理，AI 仅作工具分工」。
- **实际选择**：B。原话：「重建一版……**需求梳理写主导。claude 降级成纯工具分工**」`[一手:transcripts/user-turns.jsonl#L179]`。
- **他给的理由**：未明说，但次日自己把口径修正为「trae 进行中学作文批改和 AI 学情咨询系统的**代码生成和审查**」`[一手:transcripts/user-turns.jsonl#L193]`——从「用它做了系统」退到「用它做代码生成和审查」。
- **事后结果**：这条和他的证据洁癖同源：**可以把工具写进流程，但不让工具占「作者」位置**。`[推测]` 这也解释了他为什么反复要求 AI「不要编造」「源代码为准」（见 2.5）。

### 2.5 给 AI 定的硬规则：不许编、以源码为准、必须画负向证据

- **情境**：让 AI 用 archify 画项目链路图，AI 容易编出不存在的环节。
- **实际选择**：他在提示词里写了一整套验收条件：「不写代码里没有的东西：不画审批、不画重试、不画缓存、不画 MQ/异步」「不把教程的说法当结论，最终以源码为准」「不臆造行号；挂不准的 sources 就不挂，宁可少挂」，并要求标出「无审批环节（源码 0 命中）」这类**负向证据**`[一手:transcripts/user-turns.jsonl#L85]`。
- **他给的理由**：未解释，规则本身就是理由。
- **事后结果**：这套提示词不是一次性的，他把同样的句式复用到第 2–8 课，每次都要求「请你检查仓库代码和 @tutorial-x.md 文件内容，帮我补充完整上述提示词后进行提示词的保存并利用 archify 自行执行」`[一手:transcripts/user-turns.jsonl#L89-L95]`。**这是他极少见的、成体系的工程规范类产出**。

### 2.6 双轨并行：一边央企校招笔试，一边 AI 实习岗

- **情境**：2026 年 10 月，两条完全不同的路同时在推进。

- **他给的理由**：**这是本维度最重要的一条自述**——「秋招不太期待，反而期待我考公考研，但是我今年不想考研可能后面会考；**我的第一反应是抗拒**」`[一手:transcripts/user-turns.jsonl#L145]`；「（家里）想让我考离家较近的**事业编**岗位；最近一次起冲突是在九月份的周五，我和他们说不想考研究生」`[一手:transcripts/user-turns.jsonl#L147]`。
- **矛盾（保留，不调和）**：他说对考公考编「抗拒」，却在 10-13 至 10-20 花了一周做央企校招笔试的题。两者不完全冲突——**华电是央企校招，不是事业编**，且他投的是技术笔试（软件工程/信息安全/大数据）`[一手:transcripts/user-turns.jsonl#L155-L170]`；`[推测]` 这更像「不排斥进国企技术岗，但抗拒被安排去考事业编」的区分，而不是自相矛盾。但语料里**没有任何一句他自己做的这个区分**，所以只能标推测。

## 3. 学习决策：刷题、八股、项目优先级

### 3.1 用「做动画网页」替代「刷题量」

- **情境**：2026-10-09 至 10-11，准备算法。
- **可选方案**：A. 按题单刷量；B. 少量精做，每题做一个可视化讲解网页并推 GitHub。

## 6. 决策风格小结（全部为推测，仅供下游使用）

## 7. 本维度信息不足之处

**证据薄弱、不要据此下结论的地方：**

1. **几乎所有决策都缺「他给的理由」**。201 条发言绝大多数是祈使句指令（「帮我……」「请你……」），他极少解释为什么。本文件里「理由」一栏有近一半是「未说明」，凡是我补的都用 `[推测]` 标了。**任何把推测读成事实的用法都是错的。**
2. **没有 AI 的回复内容**。语料只有他的提问，没有 AI 的回答。所以「他为什么改主意」只能从前后两条指令倒推，无法看到他被什么说服。这是本维度最大的结构性缺陷。
3. **「央企校招 vs 抗拒考编」的矛盾无法证实**。我给的「国企技术岗可以、事业编不行」的区分是推测，语料里没有他自己做的这个区分。也可能纯粹是「先都试试」。

5. **时间戳存在 ±8 小时的不确定性**。claude 会话是 ISO UTC（可信），dsh 会话是 epoch 毫秒（换算时区假设为 UTC）。若 dsh 的毫秒值实际是本地时间，则文中「10-23 03:44 安装 archify」这类钟点会整体平移 8 小时，跨日判断可能差一天。本文已尽量只使用**时长和顺序**（时区无关），但仍有个别日期可能偏移。
