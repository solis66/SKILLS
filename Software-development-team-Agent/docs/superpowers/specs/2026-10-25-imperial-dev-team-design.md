# 三省六部软件开发团队 Agent Skill — 设计文档

日期：2026-10-25
状态：待批准

## 意图与为什么

用中国古代三省六部制度构建一个全流程软件开发团队 skill：用户（皇帝）提出需求后，由中书省（需求分析）、门下省（审核）、尚书省六部（执行）接力完成「需求 → PRD → 架构 → UI → 拆解 → 并行编码 → 审查 → 部署交付」的完整流水线，最终交付可运行的 MVP。

**为什么用这个结构**：多 agent 流水线最大的失败模式是职责重叠（齿轮打滑）和交接断层（缺齿）。三省六部天然是「决策（中书）— 审核（门下）— 执行（尚书六部）」的分权制衡结构，每个衙门只做自己那段、只对上一个人负责。把这个结构映射到软件流程，边界由工件契约强制执行，而不是靠各 agent 自觉。

## 目标 / 非目标 / 反目标

**目标**
- 一个 skill 触发后走完需求到可运行 MVP 的全流程
- 六部职责零重叠、零缝隙（齿轮咬合）
- 前后端真正并行：靠 API 契约 mock 解耦，互不等待
- 每个阶段有明确放行信号；每个问题有明确回退路由

**非目标**
- 不追求生产级产品，交付物是 MVP
- 不内置技术栈偏好（户部按项目现选）
- 首版聚焦单轮全流程 + 回退路由，不做多版本迭代运营
- 首版仅支持绿地项目（空仓库从零搭建）；在已有代码库上加功能的支持留待二期

**反目标**（技术上成功也算失败）
- 任何 subagent 修改了非自己产出的工件（越权）
- 审查者自己动手修码（齿轮打滑）
- 前后端互相等待造成伪并行
- 中途需求变更被任何一部直接吞掉而不走 中书→门下→皇帝 流程

## 约束

- 宿主 ZCode：SKILL.md + 每部一份子 agent 提示词文件 + 工件模板文件
- 调度：SKILL.md 指导主 agent（尚书省）用 Agent 工具派发 subagent；「皇帝批准」门禁用 AskUserQuestion 暂停等待用户
- 工件全部为 markdown 文件，固定章节结构，集中存放在项目仓库 `docs/imperial/` 目录
- skill 正文用中文撰写（用户为中文用户）；文件名用英文（避免 吏部/礼部 拼音撞名）

## 方案取舍（Approaches）

考虑过三种执行形态：

1. **单 agent 顺序扮演**：全部流程在一个会话里按阶段推进。简单、便宜，但「批量并行产出」只是模拟，边界靠阶段纪律维持。放弃——与用户核心诉求冲突。
2. **并行 subagent 编排（选定）**：SKILL.md 作为尚书省总调度，六部各一份提示词文件，交接走结构化工件。边界由「工件唯一 owner」规则强制执行。选它：用户要真并行；且边界强制力来自工件契约而非自觉。
3. **dynamic-workflow 全自动流水线**：全自动无人值守，但「皇帝批准」这类人机门禁在全自动工作流里处理别扭，交互灵活性差于 Agent 工具。留作未来扩展（如「皇帝已预授权全流程」模式）。

### 工件链（齿轮的齿）

所有交接只走工件，不传对话。每份工件唯一 owner，存于项目 `docs/imperial/`：

| 工件 | 文件 | Owner | 消费者 |
|---|---|---|---|
| PRD（需求带 ID + 验收标准） | `00-prd.md` | 中书省 | 门下省、皇帝、全部六部 |
| 架构决策书（技术栈/API 契约/数据模型/部署拓扑/目录规范） | `01-architecture.md` | 户部 | 吏部、礼部、兵部、刑部、工部 |
| UI 规范 + 核心页原型 | `02-ui-spec.md` + `mockups/*.html` | 吏部 | 礼部、兵部前端、刑部 |
| 任务看板（任务卡 DAG） | `03-tasks.md` | 礼部 | 刑部（预审）、兵部、主调度 |
| 审查报告（含缺陷票）+ 评测集 | `04-reviews/*.md` + `04-evals.md` | 刑部 | 兵部（修复）、工部（放行票）、皇帝 |
| 交付清单（冒烟结果/发布说明） | `05-release.md` | 工部 | 皇帝 |

### 流程时序

```
用户提需求
  → 中书省：竞品调研(web search) + 需求分析 → PRD
  → 门下省：审核（完整性/一致性/可行性/可测性）
       ├─ 驳回（带缺陷清单）→ 回中书省重写，最多 2 轮，第 3 轮带分歧呈皇帝裁决
       └─ 通过 → 呈皇帝（AskUserQuestion：准奏 / 驳回修改）
  → 户部：架构选型 → 架构决策书
  → 吏部：UI 规范 + 核心页原型（吃户部技术栈，串行于户部之后）
  → 皇帝：开工批准（架构决策书 + UI 规范/原型一次呈报）
  → 礼部：任务拆解 → 任务看板（DAG）
  → 刑部：计划预审（对照契约与 UI 规范查任务缺口，驳回回礼部）
  → 兵部：按 DAG 分批派并行工程师 agent 产码
       └─ 前端在后端未就绪时按 API 契约 mock，绝不互相等待
  → 刑部：逐卡审查（pass / reject 带缺陷票打回兵部；每卡最多 2 轮，第 3 轮呈皇帝）
  → 工部：部署 + 冒烟测试 → 交付清单
       └─ 冒烟失败 → 缺陷票经刑部回兵部
  → 皇帝验收
```

### 六部边界（核心）

**户部｜架构选型**
- 输入：已批准的 PRD。产出：《架构决策书》——技术栈（前端框架/后端语言与框架/数据库）、部署拓扑（本地/docker/云）、API 契约（接口清单 + 请求响应数据结构）、数据模型（实体与关系）、工程目录结构规范。
- 禁区：不碰 UI 设计、不拆任务、不写业务代码。
- 齿轮：**API 契约是前后端唯一对接面**。前后端都只对契约编码；改契约必须回户部。

**吏部｜UI 设计**
- 输入：PRD + 户部技术栈。产出：《UI 规范》——页面清单、每页组件清单（含加载/空/错误/边界状态）、设计 token（色/字/距）、交互说明；另附 2–3 个核心页面的静态 HTML 原型（`mockups/`）。
- 禁区：不定前端框架（户部的事）、不写生产代码（原型仅是参照物）、不拆任务。
- 齿轮：组件清单即礼部拆前端任务的单元；组件状态表即刑部查 UI 完整度的清单。

**礼部｜任务拆解**
- 输入：PRD + 架构决策书 + UI 规范。产出：《任务看板》——任务卡 DAG：ID / 范围 / **文件范围**（该卡独占的文件与目录）/ 负责角色（前端/后端）/ 验收标准（可溯源到 PRD 需求 ID 或组件 ID）/ 涉及的契约接口 / 依赖关系。
- 禁区：不做技术决策（发现不可行→上报回户部）、不改 PRD 范围（歧义→上报回中书省）、不写代码。
- 齿轮：**DAG 决定并行度**。无依赖的任务同时派给兵部多个工程师。

**兵部｜批量产码**
- 输入：任务卡 + API 契约 + UI 规范。运行：主调度按 DAG 分层派发并行工程师 subagent（前端×N / 后端×N，每批默认 2–3 个）。产出：代码 + 逐卡完成报告（改动文件、实现/消费的契约接口、自测结果）。
- 产码质量红线（六维，刑部按此逐维审查）：
  - **健壮性**：外部输入一律校验；错误全部处理（不裸抛、不吞异常）；边界与失败路径有交代
  - **可读性**：命名达意、符合语言社区惯例；注释只写「为什么」不写「是什么」
  - **可复用性**：通用逻辑抽公共模块，禁止复制粘贴式实现
  - **可维护性**：模块边界清晰、依赖单向、无循环依赖
  - **规范性**：严格遵循户部技术栈与目录规范；脚手架卡内配好 lint/格式化，代码必须过检
  - **安全性边界**：密钥凭据不硬编码（走环境变量/配置）；用户输入按不可信处理（防注入/XSS/路径穿越）；禁止 eval、拼接 SQL、未净化 innerHTML 等危险面；依赖只用架构决策书清单内的主流库（防供应链）；权限最小化
- 禁区：不重新拆任务、不改契约、不改设计意图——发现问题上报（经主调度路由），不擅自绕过；不自我宣布「完成」（完成判定归刑部）。
- 齿轮：完成报告 + 代码 diff 是刑部审查对象。

**刑部｜审查 / 观测 / 评测**
- 输入：完成报告 + diff + 各上游工件。产出：《审查报告》——逐卡 pass/reject，缺陷票（文件/严重度/修法）打回兵部；《评测集》（从 PRD 验收标准逐条生成评测用例，跨迭代累积回归）；《观测基线》（错误率/时延/关键漏斗指标清单，作为工部放行门槛）。另在兵部开工前做一次**计划预审**（对照契约与 UI 规范查任务缺口，驳回回礼部）。
- 判定标准：**机械验证必须复跑**（构建、测试套件、lint 若有），代码逻辑做静态评审；部署/运行时验证归工部冒烟。审查维度 = 兵部产码质量红线六维逐维核对 + 前后端与 API 契约的一致性。
- 禁区：**只驳回不修码**（修复永远回兵部）、不部署、不改验收标准（发现标准有问题→上报）。
- 齿轮：pass 信号 = 工部放行票；评测集 = 跨迭代回归契约。

**工部｜交付部署**
- 输入：刑部 pass + 户部部署拓扑 + 发布 tag 的仓库。产出：可运行 MVP——按户部拓扑搭建环境、部署脚本与配置、发布说明（能干什么/已知问题/如何运行）、部署后冒烟测试（对照刑部评测集核心用例）。
- 禁区：不写业务代码（只写部署/构建粘合层：CI、Dockerfile、部署脚本）、无刑部 pass 不部署、不自定部署架构（拓扑是户部定的）。
- 齿轮：冒烟失败 → 缺陷票经刑部回兵部。

### 并行写码的冲突规则与集成

- **文件范围互斥**：同批并行派发的任务卡，文件范围不得相交。共享文件（路由注册表、package.json、数据库 schema、构建配置）不进并行卡——要么划入某张卡的独占范围，要么拆成前置串行卡。
- **脚手架卡先行**：任务看板第一张总是串行的「工程脚手架卡」（按户部目录规范初始化仓库结构与构建配置、落地契约类型定义），完工后才能并行派卡。
- **调度方式**：DAG 分层串行、同层并行、同一工作树直写（不用分支，靠文件范围互斥保证安全）。
- **集成卡**：DAG 末端必有一张串行「集成卡」（依赖全部前后端功能卡）：拆除前端 mock、真联调、端到端走通契约，由兵部执行；刑部对集成结果做契约一致性审查。

### 断点续跑

任务卡带状态字段（pending / coding / reviewing / rejected / done）。SKILL.md 每次触发先扫描 `docs/imperial/` 现场工件推断进度、从断点续跑。首版承诺 best-effort 续跑，不承诺事务级恢复。

### 回退路由（全部经尚书省主调度）

主调度（SKILL.md）只做派活与路由，**不做任何设计决策**。

| 发现的问题 | 路由 |
|---|---|
| 需求歧义 / 变更 | 中书省补充 → 门下省复审（仅受影响章节）→ 皇帝批准 → 礼部只重排受影响的 DAG 子图 |
| 任务拆错 / 不可执行 | 礼部重拆 |
| 契约需要变更 | 户部改契约 → 礼部同步受影响任务 |
| 设计需要变更 | 吏部改规范 → 礼部同步 |
| 代码缺陷 | 兵部修复（刑部开票） |
| 部署故障 / 冒烟失败 | 工部排查；业务缺陷开票回兵部 |

### 门禁与循环上限

- 门下省驳回 PRD：最多 2 轮，第 3 轮带分歧呈皇帝裁决。
- 刑部驳回任务卡：每卡最多 2 轮，第 3 轮带分歧呈皇帝。
- 皇帝门禁共三处，一律用 AskUserQuestion（准奏 / 驳回 + 理由）：① **PRD 批准**（门下省通过后）；② **开工批准**（户部架构决策书 + 吏部 UI 规范与核心页原型一次呈报，准了才拆解开工）；③ **最终验收**（工部交付后）。
